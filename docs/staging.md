# Перевірка PR і staging

1. У налаштуваннях GitHub main увімкнути обов'язковий PR і required status check з назвою quality, яку GitHub покаже після першого прогону. Вимкнути обхід для тих, хто має виконувати політику.
2. У тестовому PR окремим комітом зробити навмисне порушення формату Conventional Commits. Зберегти посилання на червону дію та підтвердити блокування merge. Виправити повідомлення й перевірити зелений повтор. Локальний аналог перевіряється тією самою командою з Git-діапазоном.
3. Погодити платний staging і створити Render Blueprint з render.yaml. Приватній staging-БД не потрібен зовнішній доступ. Якщо сервіс і БД вже існують, звірити налаштування Blueprint перед застосуванням.
4. У GitHub environment staging задати secret RENDER_API_KEY та variables RENDER_SERVICE_ID, STAGING_URL. Значення STAGING_URL має бути HTTPS-адресою сервісу. Дозволити розгортання з main.
5. Після merge перевірити job staging, запис Render deployment, 200 /ready та рівність SHA в /version і GitHub. За потреби окремо запустити node dist/maintenance/seed.js з Render Shell, тільки на демонстраційній БД.
6. При зміні схеми узгоджувати кроки expand/contract зі старою активною версією. Великі індекси запускати окремою операцією з образу до розгортання. Після перерваного CREATE INDEX CONCURRENTLY перевірити pg_index. Якщо індекс існує та є invalid, підготувати явний ремонт перед повтором. Міграційні файли після застосування залишати незмінними.

Локальна перевірка make container-check збирає образ із HEAD, створює одноразову мережу й PostgreSQL, перевіряє 503 від /ready без індексів, застосовує їх окремою командою і перевіряє 200, SHA та Docker health status.
