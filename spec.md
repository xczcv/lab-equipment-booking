# Бронювання обладнання

Робоча специфікація спирається на сценарії з початкового README. Початковий опис надав власник проєкту. Код і робоча документація підготовлені за участі OpenAI Codex. Додані деталі контракту й ADR очікують погодження студента.

## Компоненти та дані

Точка входу ініціалізує ресурси. HTTP-шар читає запит і формує відповідь. Каталог та бронювання виконують прикладні операції. Сховище читає й змінює стан. У ЛР1 реалізовано тільки точку входу, HTTP-шар і маршрут здоров'я.

- Один прилад має багато слотів. Слот містить початок і завершення в UTC.
- Один студент має багато бронювань. Бронювання пов'язує студента зі слотом і містить стан скасування.
- Слот може мати кілька історичних бронювань і щонайбільше одне активне.
- Запис ідемпотентності пов'язує студента, ключ, параметри створення й відповідь.

## Сценарії

1. Каталог показує тестові прилади. Пошук повертає вільні майбутні слоти в межах календарного дня Europe/Kyiv.
2. Створення перевіряє слот і фіксує бронювання. Для одночасних запитів з різними ключами успішний рівно один запит. Суперник отримує 409.
3. Повтор з тим самим ключем і даними отримує первинну успішну відповідь.
4. Студент бачить тільки власні бронювання. Скасування залишає запис у історії та звільняє майбутній слот.
5. GET /health повертає 200 та JSON зі статусом ok, коли процес відповідає.

## Аудит ЛР1

У зібраному застосунку HTTP-модуль відокремлений від запуску процесу. Smoke-тест звертається до збірки через справжній HTTP-запит. Три потенційно зайві залежності на цьому етапі — HTTP-фреймворк для одного маршруту, ORM без БД і тестовий фреймворк замість вбудованого node:test. Їх не додано.

## HTTP-контракт ЛР2

| Метод і шлях                             | Успіх | Сценарій                                                            |
| ---------------------------------------- | ----- | ------------------------------------------------------------------- |
| GET /equipment                           | 200   | Масив приладів із числовим id та назвою                             |
| GET /equipment/:id/slots?date=YYYY-MM-DD | 200   | Масив доступних слотів із часом початку й завершення в UTC          |
| POST /bookings                           | 201   | JSON з єдиним полем slotId і обов'язковий заголовок Idempotency-Key |
| GET /bookings                            | 200   | Історія поточного користувача, включно зі скасованими               |
| POST /bookings/:id/cancel                | 200   | Скасована бронь, повтор повертає той самий стан                     |

Для операцій бронювання клієнт передає X-User-Id (student-a або student-b). Це заголовок демонстраційної ідентичності. Усі відповіді мають X-Business-Process-Id. Невідомі прилади, слоти та недоступні користувачу бронювання повертають 404. Відсутній або невідомий студент отримує 401. Некоректні параметри повертають 400, неправильний тип тіла 415, тіло понад 4096 байтів 413. Зайнятий слот, слот із часом початку не пізніше поточного часу та повтор ключа з іншим слотом повертають 409 з різними кодами. Ключ має область дії одного користувача, зберігає тільки успішну відповідь і повертає її навіть після скасування.

## PostgreSQL

Таблиці equipment, students і slots тримають каталог, студентів і готові інтервали. bookings зберігає власника, час створення та nullable cancelled_at. Частковий унікальний індекс bookings_one_active_idx діє на slot_id, поки cancelled_at IS NULL. booking_receipts має ключ (user_id, request_key), slot_id і первинну JSON-відповідь.

Створення резервує ключ у транзакції READ COMMITTED. Повтор з тим самим ключем чекає результату першої транзакції, далі окремим запитом читає запис. Новий запит бере блокування рядка слота, окремо читає актуальну активну бронь, застосовує правила, вставляє бронювання та зберігає відповідь перед COMMIT. Будь-який збій відкочує обидва записи. Після 503 клієнт може повторити запит із тим самим ключем. За невизначеного для клієнта результату COMMIT повтор поверне збережену відповідь, якщо сервер БД завершив COMMIT.

Пошук використовує один запит з NOT EXISTS замість запиту до кожного слота. Межі дня походять з двох місцевих півночей Europe/Kyiv і перетворюються в UTC окремо. Пошук відрізняє порожній день від невідомого приладу. Отримання історії виконує один запит з умовою власника після його перевірки.

### Аудит ЛР2

1. Демонстраційний заголовок ідентичності дозволяє видати себе за іншого тестового студента. Дані для стенда мають бути тестовими.
2. Створення за межами часу слота відхиляється за годинником застосунку після отримання блокування. Пошук і бронювання можуть бачити різні стани через конкурентний запит.
3. Ключі успішних створень живуть разом з історією. Політику зберігання та видалення потрібно погодити окремо. Відмова PostgreSQL дає 503 для відомих тимчасових помилок. Порушення інваріантів або помилки коду дають 500.

## Перевірка ЛР3

Інтеграційні сценарії працюють на окремих схемах PostgreSQL із випадковими іменами. Тест конкурентності спостерігає дві незалежні SQL-сесії в очікуванні блокування одного слота, а після завершення звіряє 201, 409 та один активний запис. E2E запускає зібрану точку входу окремим процесом і перевіряє повний життєвий цикл бронювання через HTTP.

Перший паралельний прогін зафіксував 40P01 між SELECT pg_advisory_lock та CREATE INDEX CONCURRENTLY. Очікування блокування замінено повторними викликами pg_try_advisory_lock без довгоживучого знімка. Повторний прогін пройшов.

## CI, CD та перевірка готовності ЛР4

GitHub Actions перевіряє формат, лінт, збірку, smoke, тести на окремій PostgreSQL, Dockerfile та повідомлення Conventional Commits. Захищена main вимагає зелений job quality перед merge. Успішний push на main запускає staging job, який передає Render SHA коміту. Після завершення job звіряє готовність і SHA публічного API.

GET /health перевіряє процес. GET /ready перевіряє доступність БД, таблиць і валідність робочих індексів. GET /version повертає JSON із SHA збірки. Контейнер запускає короткі структурні міграції перед процесом HTTP. Окремий pre-deploy крок готує індекси CONCURRENTLY. Seed і майбутні backfill виконуються окремо. Сумісність змін зі старим екземпляром підтримується до приймання трафіку новим.

## Виміри ЛР5

make load відтворює три прогони. На кожному створюється нова схема з 48 приладами, 60 календарними днями і 32 слотами на день. Близько 20% слотів більшості приладів попередньо зайнято. Після прогріву сценарій пошуку робить 1800 GET за 12 паралельних клієнтів. Для бронювання 100 груп по 12 запитів з різними ключами змагаються за свої вільні слоти. Кожна група повинна дати один 201 і одинадцять 409.

make profile повторює обидва сценарії з V8 CPU profiler. Сервіс звіряє /version із SHA чистої ревізії до виміру. Зберігаються сирі HTTP-замірювання, SQL-тривалість по операціях, перцентилі, CPU, event-loop idle, RSS і EXPLAIN ANALYZE того самого SQL. PostgreSQL працює ізольовано, клієнт і Node.js API виконуються на локальній машині.
