# Бронювання обладнання університетської лабораторії

Студент обирає прилад і бачить, коли ним можна скористатися. Він бронює вільний час і може скасувати власну бронь. Наприклад, якщо двоє студентів одночасно бронюють осцилограф на 14:00, один отримує бронь, а другий бачить, що цей час уже зайнятий.

Це план першої версії. Сценарії перевіряємо через HTTP API на Node.js. На початку працюємо з даними в пам'яті, потім переносимо їх у PostgreSQL.

## Що має вміти сервіс

| Дія | Запит |
| --- | --- |
| Переглянути каталог приладів | `GET /equipment` |
| Знайти вільний час для приладу на конкретний день | `GET /equipment/:id/slots?date=YYYY-MM-DD` |
| Забронювати слот | `POST /bookings` з `slotId` |
| Переглянути свої бронювання | `GET /bookings` |
| Скасувати своє бронювання | `POST /bookings/:id/cancel` |

У першій версії використовуємо готові слоти. Кожен слот належить одному приладу й має час початку та завершення. Час зберігаємо в UTC, а дату в пошуку трактуємо в часовому поясі лабораторії `Europe/Kyiv`.

- Слот у минулому забронювати не можна. Для вже зайнятого слота API повертає `409 Conflict`.
- Скасована бронь залишається в історії. Якщо слот ще не почався, його знову можна забронювати.
- Повтор створення броні з тим самим ключем ідемпотентності й тими самими даними повертає результат першого успішного запиту.

Модель складається з `equipment`, `slots`, `bookings` та `users`. Бронювання пов'язує студента зі слотом. Для демонстрації достатньо кількох тестових приладів і облікових записів.

## Порядок роботи

1. **ЛР1. Структура проєкту.** У `spec.md` описати модель, межі каталогу, пошуку слотів і бронювання. У `standards/` зафіксувати формат специфікацій, ADR і перевірки перед здачею. Підняти `GET /health`, налаштувати форматування, лінтер, збірку, smoke-тест і Git hooks. Показати, що hook зупиняє коміт із порушенням.
2. **ЛР2. Працюючий API та база.** Окремим комітом зафіксувати всі п'ять маршрутів на даних у пам'яті. Потім перенести зберігання в PostgreSQL. Створення броні й запис для ідемпотентного повтору виконувати в одній транзакції. Унікальний частковий індекс на `slot_id` для активних броней має витримувати одночасні запити. Роути відповідають за HTTP, сервіс за правила бронювання, репозиторій за SQL і транзакції. Один глобальний обробник перетворює помилки на HTTP-відповіді. Business-process ID має бути в логах від HTTP-запиту до результату операції з БД. У `adr/` описати вибір БД і спосіб передавання ресурсів та контексту запиту.
3. **ЛР3. Перевірка бронювання.** Unit-тести покривають усі гілки правила доступності слота. Інтеграційний тест з PostgreSQL запускає два незалежні запити на один слот і перевіряє, що активна бронь одна. E2E проходить від пошуку до скасування й повторного бронювання. Додати `make test`, `make mutation` і розібрати мутантів, які вижили.
4. **ЛР4. Публічний стенд.** GitHub Actions перевіряє формат, лінт, збірку, тести й Conventional Commits. Показати, що помилка в PR блокує merge. Після merge в основну гілку контейнер автоматично розгортається на staging і запускає міграції. CI використовує окрему тестову БД. На стенді `/version` повертає SHA розгорнутого коміту.
5. **ЛР5. Швидкодія.** Окремо виміряти пошук вільних слотів і паралельне бронювання. Через `make load` та `make profile` повторити прогони на тих самих даних, зібрати p50/p95/p99, CPU, пам'ять і час очікування. Запит на пошук слотів перевірити через `EXPLAIN ANALYZE`. За вимірами вибрати модуль для окремої TypeScript-бібліотеки. Залежності передати через її публічний контракт і повторити заміри після рефакторингу.

Для кожної лабораторної потрібні посилання на її GitHub PR і окремий DEFENSE. До `spec.md` переносимо погоджені сценарії та рішення. DEFENSE студент пише за власними результатами.
