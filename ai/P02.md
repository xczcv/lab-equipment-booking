# P02 · Доопрацювання матеріалів після аудиту

24 листопада 2026. Запит передано OpenAI Codex у повідомленні з технічним дорученням. Заголовки фрагментів додано для посилань. Службові заголовки й персональні дані вилучено.

## P02-scope

> Користувач дозволив доопрацювати локальні артефакти здачі ЛР1–ЛР5 для [вилучено персональні дані] після аудиту DoD. Продовж у своєму наявному репозиторії. Локальні зрізи `lab-01`–`lab-05`, поточна гілка `feature/booking-labs`. Реальний приклад для аудиту є в `evidence/lab03-mutation-analysis.md`: п'ять вижилих мутантів і коміт `414b0c4`. Звір фактичні деталі.

## P02-LR4

> У `docs/staging.md` звір сценарій навмисного порушення з тим, що перевірка Conventional Commits охоплює весь діапазон PR: окремий виправний коміт не прибирає поганий subject із діапазону. Запропонуй для демонстрації негативний тест, який можна виправити окремим комітом, і познач його в документації.

## P02-spec

> Зроби коротку специфікацію для кожної ЛР до однієї сторінки з метою й вимірюваними критеріями приймання, легко знайдену з README. Збережи корисні деталі наявної накопичувальної специфікації. Познач як чернетки ті вимоги та рішення, які студент ще має погодити. Додай ADR у форматі MADR на ключове рішення ЛР1, описавши фактичні альтернативи й наслідки, без твердження, що студент вже погодив рішення.

## P02-AI

> Створи в репозиторії ai/ з реальним слідом використання AI. У своїй історії доступний первісний фактичний запит від 23 листопада до всіх п'яти лаб. Збережи його один раз під стійким локальним ідентифікатором на зразок P01 і віднеси до ЛР1–ЛР5 через посилання на відповідні фрагменти, коміти і перевірки. Окремі записи додавай лише для запитів, які справді існували. Збережи суттєвий технічний текст, дату, а також подальші фактичні промпти, що вплинули на результат. Прибери приватні абсолютні шляхи, персональні дані й службові деталі середовища. Познач вилучення. У матеріалах для здачі використовуй локальні Markdown-посилання, без назв чи URL платформи оркестрації. Факт використання OpenAI Codex відображай прозоро. Не перетворюй один реальний запит на п'ять вигаданих та не створюй фіктивний діалог.

## P02-audit

> По кожній ЛР звір три реальні розбіжності або зрізані кути з доступними доказами. Для кожної вкажи відповідний промпт або його фрагмент, фактичне спостереження, фідбек-коментар (новий можна додати поточною датою з чесною атрибуцією), уточнений критерій чи стандарт, ревізію виправлення, команду та результат. Якщо старого фідбеку чи підтвердження нема, назви це прямо. Не вигадуй знахідок заради заповнення трьох рядків. Для нових перевірок зберігай тільки фактичний результат.

## P02-submission

> Зроби в README або окремому короткому індексі по ЛР1–ЛР5 входи на spec, ADR, аудит, команду, докази, відповідний SHA і стан майбутнього PR. Студент сам заповнює односторінковий DEFENSE: мета 1–2 речення, топ‑3 з комітами, рішення й альтернативи з ADR, команда перевірки, її результат і SHA з /version там, де ендпойнт існує. Можеш зібрати посилання й факти як підготовку, зберігаючи авторство; не пиши DEFENSE від імені студента.
>
> Перевір узгодженість індексу з реальними ревізіями й файлами. Зафіксуй зміни нормальними новими локальними комітами, історію існуючих комітів не переписуй. GitHub PR, push, зовнішнє розгортання і зміни в GitHub залишаються окремими діями після підтвердження. Для ЛР4 залиш у документації конкретні кроки і відділи локальні докази від ще не підтверджених GitHub checks, merge gate та публічного staging. МКР тут не виконувати, умови ще нема. Продовж без підлеглих агентів і наприкінці коротко наведи результат та блокери.
